# Session 01, 12 September 2026

Purpose of this log: the third skill on the map is using coding agents, and that skill
is exercised by how this repo gets built rather than by anything inside it. So this
records what the agent was given, what it got wrong, and what fixed it.

## Context given at the start

A four-part blog series to learn from, a company website to imitate, a preference for
the frontend-design skill, and an instruction to follow standard engineering practice.
No stack, no scope, no data.

That is a normal amount of context for a real task and not enough to build from. Two
rounds of numbered questions with stated defaults closed the gap. The defaults mattered
more than the questions: a question with no default forces a decision the asker may not
have, and a question with a default can be answered with one word.

## Defect 1: recommending a stack from the wrong evidence

The agent proposed a TypeScript monorepo. The reasoning was that the repo already
contained a working pnpm and Turborepo project, so reuse was cheapest.

The reasoning was fine. The evidence was wrong. Aries Global publishes its own
engineering job specs, which state that the codebase is "90%+ Ruby", that backend work
is in Ruby and Python, and that the front end is React. None of that was checked before
recommending.

Fixed by reading the job specs. The corrected decision is ADR 0001.

Lesson: when a question is about the world rather than about a preference, look it up
before offering an opinion. The user cannot be expected to correct a recommendation
whose basis they cannot see.

## Defect 2: citing sources that were never read

The egress proxy in this environment blocks `deeplearning.ai`, `x.com`,
`aries.global`, and every mirror of the skills map found. The map's contents were
reconstructed from search-result summaries.

That is a real limitation and it was stated rather than hidden. `docs/skills-map.md`
reproduces the structure at the confidence level the sourcing supports. If the primary
text becomes available, that file is the one to correct.

Lesson: an unverified claim presented at the same confidence as a verified one is the
failure mode that costs the most trust later.

## Environment notes

Docker daemon is not running, so Postgres runs directly from
`/usr/lib/postgresql/16/bin`. pgvector was absent and installed from apt as
`postgresql-16-pgvector` 0.6.0. Ruby 3.3.6 through rbenv, with `rails` at
`/opt/rbenv/versions/3.3.6/bin` rather than on the default PATH. Python 3.11 with uv.

## Decisions taken without asking

Eight fictional company names, their countries, verticals and ARR split totalling the
EUR 70.0M that was specified. These are routine judgement calls and asking about each
would have wasted a round.

The defect classes planted in the synthetic data were not routine, because they
determine what the eval harness can measure. They are written down in ADR 0004 rather
than left in code, so they can be argued with.

## Defect 3: a coverage rule that inferred too little

The first version of the row-level security coverage spec decided a table was
tenant-scoped if it carried a `company_id` column. That rule missed `agent_runs`,
which scopes itself by an array of company ids and holds tool inputs and outputs
in its `trace` column. Tenant data, no `company_id`, no policy, and a spec that
reported full coverage.

Fixed by inverting the rule. Every table is tenant-scoped unless it appears in an
explicit exemption list. Deny by default catches the next table shaped like that
one; inference only catches the tables you already thought of.

## Defect 4: schema.rb cannot represent the thing being tested

Rails dumps `db/schema.rb` by default, and it can express tables and indexes but
not policies, functions or grants. The test database is rebuilt from that dump.

So the isolation suite would have run against a test database with no row-level
security, no `mars_company_ids()` function, and no revoke on the answer key.
Every isolation spec would have passed while asserting nothing, which is worse
than having no specs, because it produces confidence.

Fixed by setting `config.active_record.schema_format = :sql`. Verified by
grepping the dump: 21 policies, 21 FORCE statements.

## Defect 5: privileges are not schema, and are lost anyway

`pg_dump` writes schema without privileges, so even `structure.sql` drops the
`REVOKE ALL ON ground_truths FROM mars_app`. That protection existed in
development and vanished from CI on every rebuild.

Fixed with a `mars:harden` task hooked onto every task that rebuilds a schema.
The first version of it hardened the wrong database: `db:test:prepare` runs
inside a development process, so the ambient connection points at development,
and the task reported success against the database nobody was testing. It now
resolves the target environment's config explicitly.

Lesson: a protection expressed in a layer your tooling does not round-trip is not
a protection. Check what actually survives a rebuild.

## Defect 6: a spec that tested the wrong layer and passed

The write-isolation spec asserted that creating a record with another company's
`company_id` raised an error. It did, and for the wrong reason: the `belongs_to`
validation fired first, because the foreign company row is invisible.

That proves the application is careful. It proves nothing about the database,
which is the actual boundary, and it is precisely the path a bulk insert skips.

Split into three specs: the validation layer, the same write with validations
skipped, and a raw SQL insert touching no model. The last two are the ones that
test ADR 0002.

## Verifying the gates by breaking them

A gate nobody attacks is not known to work. Each guarded property was broken in
the test database and the suite re-run:

| Break | Result |
| --- | --- |
| `ALTER TABLE customers DISABLE ROW LEVEL SECURITY` | 8 of 16 fail |
| `ALTER ROLE mars_app BYPASSRLS` | 10 of 16 fail |
| `GRANT SELECT ON ground_truths TO mars_app` | the answer-key spec fails |

Restored, 16 of 16 pass. The suite detects all three.

## Defect 7: a dependency incompatibility, not a code bug

Every write to a jsonb column raised `ArgumentError: wrong number of arguments
(given 2, expected 1)` from deep inside ActiveRecord. The cause: activesupport
8.1.3.1 calls `JSON.parse(source, options)`, a two-argument form that json 3.0
removed, and Bundler resolves json 3.x by default.

Pinned to `json ~> 2.7`. Worth recording because the backtrace pointed at
`Contract.insert_all!`, which was not the problem, and Rails filters gem frames
out of the trace by default. The fix was visible only after asking for the
unfiltered backtrace.

## Defect 8: a guard that caught a real rounding bug

The generator allocates each company's headline ARR across its customers, then
raised "ARR allocation drifted for northquay" on the first full run.

It was allocating the annual figure and then dividing by twelve to get monthly
recurring revenue, which rounds once per customer. The annualised sum therefore
drifted from the headline by up to six cents times the customer count, which for
Deskwright's 140 customers is most of a euro.

Fixed by allocating the monthly figure and multiplying back up, which rounds once
per customer on a number that is then scaled, bounding total drift at twelve
cents per company however many customers it has. There is now a spec asserting
that bound for all eight.

The guard was written before the bug appeared, on the assumption that an exact
total was worth checking. It paid for itself on the first run.

## Defect 9: a matcher that was always going to pass

Five generator specs failed with `undefined method 'positive?' for an instance of
RSpec::Matchers::BuiltIn::Be`. The cause was `be.positive?` where `be_positive`
was meant.

Worth noting because of the near miss. `be.positive?` raises here, which is why
it was caught. In a context where the error were swallowed, the assertion would
have silently evaluated to a truthy matcher object and passed regardless of the
value. Assertions that can only pass are worse than no assertions.

## The generator suite was too slow, and why that mattered

Eighteen examples each rebuilt the whole portfolio: 2 minutes 54 seconds. Moved
seeding to `before(:context)` and tagged the file so the global per-example
truncation skips it, down to 60 seconds.

Speed is not the point. A suite slow enough to avoid running is a suite that stops
catching things, and this one guards the data every eval grades against.

## Defect 10: a CI workflow that could not pass

A pull request opened against this branch, which meant the CI workflow would run
for the first time. It was written in the first commit alongside the ADRs, before
any of the code it referenced existed, and it was broken in three ways at once.

Two of its four jobs ran `cd intelligence` and `cd web`, directories that do not
exist yet. The eval job depended on both. And the platform job never created the
`mars_app` role, so every isolation spec would have failed for want of a login
rather than for want of a policy.

Rewritten to contain only the platform job. The others arrive in the commits that
create their directories. Making them tolerate a missing directory was the obvious
alternative and the wrong one: a job that passes because it found nothing to run
reports a green check that means nothing, which is the failure mode ADR 0003
exists to avoid.

Two further problems surfaced only by reproducing CI's conditions locally, which
is the reason to reproduce them rather than push and watch:

The owner role is deliberately not a superuser, and pgvector installs only as one
unless the extension is marked trusted. Locally that was solved by editing the
extension's control file, which is not possible inside a service container.
Installing pgvector into `template1` instead means every database created
afterwards inherits it, including the ones `db:test:prepare` drops and recreates.

That fix then exposed the next one. `pg_dump` writes `COMMENT ON EXTENSION
vector`, and replaying that statement requires owning the extension, which the
owner role does not when the extension is inherited. Loading the dump failed with
"must be owner of extension vector". Fixed by dumping with `--no-comments`, since
nothing here depends on database comments. The alternative was granting the owner
role superuser, which trades a real privilege for a cosmetic line of SQL.

Verified by tearing down the runtime role and the test database entirely, then
running the four provisioning steps and the three build steps exactly as the
workflow declares them. 34 examples, 0 failures.

Lesson: a CI workflow written before the code it runs is a guess. This one was
committed with the specifications, which was the right instinct and produced a
file that asserted a repository that did not exist.

## Defect 11: a planted defect that could not be cited

The corpus spec asserting that every planted revenue leak has its breached clause
in a document failed on `seat_growth_unbilled`. The contract it was planted on
had no committed user count, so the generated agreement had no clause 3, and
nothing had in fact been breached.

The cause was in the planting rather than the spec. Targets for the first three
leak kinds were picked from whatever contracts were left over after the uplift
and discount candidates were taken, with no check that the leftover contract had
the term the leak is supposed to breach.

An agent asked to find that leak would have been marked wrong for failing to
quote a document that says nothing on the subject. A defect that cannot be
evidenced is not a defect, it is noise in the answer key, and it silently lowers
every recall figure the harness reports.

Fixed by giving each leak kind a precondition and planting it only on a contract
that satisfies it. Revenue leaks went from three per company to four, because
all four kinds now find a valid target rather than three finding one by luck.

Lesson: the spec that caught this was written to check citability, not planting.
Asserting the property you actually depend on finds bugs in places you were not
looking.

## Defect 12: a spec that could not fail for the right reason

The scoped-retrieval isolation spec looked up another company's document with no
grant established, so row-level security correctly returned nil and the spec died
on `NoMethodError: undefined method 'id' for nil`.

It was red, so it got fixed. Had the lookup been wrapped in anything that
tolerated nil, it would have passed while asserting nothing, which is the same
trap as Defect 6 in a different costume: the mechanism under test quietly
preventing the test from reaching the assertion.

## Defect 13: three specs passing on ordering luck

The overdue-invoice rollup spec failed comparing 2,852,037 against 8,556,111,
exactly one third. The rollup was right; the spec was reading an arbitrary row.

`MetricValue.for_key("overdue_invoice_cents").find_by!(company_id:)` returns
whichever row the planner hands back first, and because the file is tagged
`:seeded` the per-example truncation is skipped, so rows written by an earlier
example for other months were still in the table. The spec compared July's
figure against a September expectation.

The two metric specs beside it had the same bug and were passing, because the
row that happened to come back first happened to be the right one.

Fixed with a `latest(key)` helper that names the period explicitly. Lesson: when
a suite deliberately shares state between examples, every assertion has to name
the row it means. "The one I just wrote" is not an identifier.

## The zero that would have read as a fact

`metrics:show` printed `median_onboarding_days 0.0 (n=0)` for September. No
onboardings completed that month, so there was no median, and the rollup wrote
zero because the SQL coalesced an empty set.

Nothing failed. It is a plausible-looking number in a table an agent is entitled
to quote, and it means "time to value is zero days", which is both false and
flattering. An agent reading it has no way to tell it apart from a real figure.

Fixed by splitting the metrics in two. Some are genuinely zero when empty: no
overdue invoices really is zero overdue. Others are unknowable when empty: no
completions is not a median of zero. The unknowable ones are omitted entirely,
so absence means absence, and an agent has to say it does not know rather than
read a placeholder as a measurement. A stale row is deleted when its metric
becomes unknowable, so an old figure cannot outlive the data that justified it.

97 of 672 values were placeholders. None of them was wrong in a way any test was
looking for.

## Defect 14: the invariant spec caught its own author

The API's authentication path stamped `last_used_at` on the token, and the first
version wrapped that write in `ApplicationRecord.as_owner`, reasoning that the
grant had not been established yet.

The coverage spec written in the second commit rejects `as_owner` anywhere in
`app/` outside `application_record.rb`, and it failed. The reasoning was wrong:
`api_tokens` carries no policy, so the runtime role can write it directly and the
bypass bought nothing. An unnecessary privilege escalation in the authentication
path is the last place to leave one.

Removed, one line. The value here is that the spec was written weeks of work
before the code that violated it, by the same author, for a rule that felt
obvious at the time and was not obvious in the moment it mattered. That is what
a gate is for.

## The API, smoke tested rather than assumed

Three tokens against a running server, same endpoints:

| --- | --- | --- |
| Group operator, 8 grants | 8 companies, EUR 70.0M | 200 |
| Portco exec, 1 grant | 1 company | 404 |
| No token | 401 | 401 |

A retrieval query scoped to `VAU-0041` returned that contract's clause 4.2 with
its citation. The same query from a token granted only Clausemark returned zero
results rather than an error, because the caller should not learn that the
document exists.

None of that was asserted by reading the code. It was run.
